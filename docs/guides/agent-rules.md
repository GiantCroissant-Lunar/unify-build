# Agent Rules and Skills

This repository is worked on by several AI coding agents, each of which reads its instructions
from a different file in a different format. Rather than maintaining those files by hand and
letting them drift, the repository keeps **one canonical source** and generates the rest.

If you have ever opened `CLAUDE.md` and wondered why it is four lines long, this page explains it.

## The canonical source

`AGENTS.md` at the repository root is the single tracked source of agent guidance. Every
tool-specific file is derived from it or from the workspace skill library.

**Edit `AGENTS.md`. Never edit a generated pointer file** — your changes will be overwritten on the
next sync, and because the generated files are gitignored, they will not even show up in
`git status` for review.

## What is tracked vs. generated

| Path | Status | Role |
|---|---|---|
| `AGENTS.md` | **tracked** | Canonical agent guidance |
| `.agent/adapters/` | **tracked** | Adapter configuration (what gets generated, and where) |
| `.agent/skills/` | **tracked** | Skills owned by this repository |
| `CLAUDE.md` | generated, gitignored | Thin import shim pointing at `AGENTS.md` |
| `.agents/` | generated, gitignored | Cross-CLI skill surface |
| `.kiro/` | generated, gitignored | Kiro IDE skills + steering files |

`CLAUDE.md` carries a `<!-- Generated by sync-project.py — do not edit. -->` header for exactly
this reason.

## Adapters

Adapter configuration lives in `.agent/adapters/`, split by responsibility.

### Targets — surfaces that get generated

`.agent/adapters/targets/<name>/config.yaml`

| Target | Generates | Why |
|---|---|---|
| `agents` | `.agents/skills/` (symlinks) | The open Agent Skills spec, read natively by Codex, Copilot, Kimi, OpenCode, and Kilo — and by Claude Code through its compatibility layer |
| `claude` | `CLAUDE.md` | Claude Code reads `CLAUDE.md` as its project instruction file, so it gets an import shim rather than a copy |
| `kiro` | `.kiro/skills/` + `.kiro/steering/*.md` | Kiro reads neither `.agents/skills/` nor `AGENTS.md`, and wants one file per rule in its own steering format |

Each target declares its skills from two pools: `local` (from this repo's `.agent/skills/`) and
`workspace` (from the shared workspace skill library). The `kiro` target additionally lists the
rules to emit as individual steering files.

### Runners — CLI invocation metadata

`.agent/adapters/runners/<name>/config.yaml`

Runners generate nothing. They record how to invoke a CLI that already consumes an existing
target — its executable name, non-interactive invocation, model-override flag, and which files it
reads for context.

`kilo` and `opencode` are runners because both read `AGENTS.md` and `.agents/skills/` natively;
the `agents` target already covers them.

## Running a sync

```bash
python tools/sync-agent-resources.py
```

Synchronize a single adapter by leaf name or by qualified path:

```bash
python tools/sync-agent-resources.py --provider agents
python tools/sync-agent-resources.py --provider targets/agents
```

Providers are discovered by scanning `.agent/adapters/` for `config.yaml` files, so adding a new
adapter is a matter of adding a directory with a config — no changes to the script.

!!! warning "Requires the workspace layout"
    `tools/sync-agent-resources.py` is a thin wrapper. It walks **up** the directory tree looking
    for `.agent/scripts/sync-project.py` at the workspace root and delegates to it. That script is
    not part of this repository. In a standalone clone the wrapper exits with
    `ERROR: workspace sync script not found searching upward from …`.

    This is expected. Nothing in the build depends on the sync — the generated files are
    gitignored conveniences for local agent tooling.

## Adding a rule

1. Add the rule to `AGENTS.md`.
2. If Kiro should see it as a separate steering file, add its name to the `rules.workspace` list in
   `.agent/adapters/targets/kiro/config.yaml`.
3. Run the sync.
4. Commit `AGENTS.md` and any adapter config change. The generated files are gitignored and should
   not appear in the commit.

## Adding a skill

Repository-owned skills live in `.agent/skills/<skill-name>/SKILL.md`. After adding one, list it
under `skills.local` in each target that should expose it, then run the sync.

Skills drawn from the workspace library are referenced by their category path — for example
`04-tooling/unify-build` — under `skills.workspace`.
